# User Story: Guest Account Provisioning and Social Identity Authentication

---

## Summary

- **As a** property seeker browsing listings without a prior account,
- **I want to** provision a guest account using Google authentication, Facebook login, or email and password,
- **So that** I can securely authenticate my identity, persist my preferences across devices, and unlock saved listing features.

---

## Scope in/out

- **In Scope:** Guest authentication modal triggering when saving favorites or initiating visit scheduling, social authentication integration via Google OAuth 2.0 / OpenID Connect and Facebook Login, native Email and Password registration and sign-in flow (password hashing via Argon2id/bcrypt, email format validation), issuing secure HTTP-only JWT session tokens, and automatic migration of ephemeral guest session cookies into the newly authenticated profile.
- **Out of Scope:** Internal broker administrative login (handled in tenant admin runbooks) and managing favorites lists (handled in [[sto-202610121709]]).

---

## Preconditions

1. Tenant identity provider configured with Google OAuth client ID and Facebook App ID credentials.
2. Tenant user account database initialized with encryption at rest per [[req-202609121910]].
3. LGPD user privacy and consent policies established per [[req-202609121913]].

---

## Expected behavior

When an unauthenticated seeker clicks to save a property or clicks "Entrar" (Log in), an authentication modal appears presenting one-click social buttons ("Continuar com Google", "Continuar com Facebook") alongside an email/password form. Upon successful authentication, the system creates or retrieves the user profile, issues a secure session token, merges any active guest favorites, and returns the seeker to their exact browse state.

---

## Acceptance criteria

### Criterion 1: Authentication Modal and Provider Options
- **Given** an unauthenticated property seeker on the portal,
- **When** the seeker clicks "Entrar" (Log in) or attempts to save a property to favorites,
- **Then** the platform must open an authentication dialog displaying:
  1. "Continuar com o Google" button
  2. "Continuar com o Facebook" button
  3. "Entrar com E-mail e Senha" form (with toggle to "Criar Conta" / Sign up)

### Criterion 2: Google Social Authentication Flow
- **Given** a seeker choosing Google sign-in,
- **When** the seeker clicks "Continuar com o Google",
- **Then** the platform must initiate Google OAuth 2.0 authorization, validate the returned ID token, extract the verified email and name, and provision or authenticate the user record.

### Criterion 3: Facebook Social Authentication Flow
- **Given** a seeker choosing Facebook sign-in,
- **When** the seeker clicks "Continuar com o Facebook",
- **Then** the platform must initiate Facebook Login flow, validate the access token, retrieve verified email and public profile, and establish the user session.

### Criterion 4: Native Email and Password Registration and Sign-In
- **Given** a seeker choosing direct email credentials,
- **When** the seeker submits valid email and password (minimum 8 characters with numbers and letters),
- **Then** the platform must hash the password securely, store the user profile, issue an HTTP-only session cookie or JWT, and log the user in without page reload.

### Criterion 5: Guest Session Data Migration
- **Given** a seeker who selected favorite properties during an anonymous browsing session,
- **When** the seeker completes authentication via any supported method (Google, Facebook, or Email),
- **Then** the platform must automatically merge the anonymous session favorites into the authenticated user profile database record without duplicate entries.

## Contracts and data

- **Auth Endpoints:**
  - `POST /api/v1/auth/google` - Payload: `{ "id_token": "google_jwt_string" }`
  - `POST /api/v1/auth/facebook` - Payload: `{ "access_token": "fb_token_string" }`
  - `POST /api/v1/auth/register` - Payload: `{ "email": "seeker@example.com", "password": "securePassword123" }`
  - `POST /api/v1/auth/login` - Payload: `{ "email": "seeker@example.com", "password": "securePassword123" }`
- **Example Auth Success Response Payload:**
```json
{
  "user": {
    "id": "usr-seeker-889",
    "email": "seeker@example.com",
    "name": "Maria Silva",
    "provider": "google",
    "created_at": "2026-10-12T17:08:00Z"
  },
  "session": {
    "token": "eyJhbGciOi...",
    "expires_in": 2592000
  },
  "migrated_favorites_count": 2
}
```

## Business rules

1. All user credentials and personal identifiers must be encrypted and stored in the tenant's isolated database partition per [[req-202609121910]].
2. User consent to terms of service and LGPD data processing must be explicitly registered upon account creation per [[req-202609121913]].
3. Passwords must never be stored in plaintext and must be hashed using industry-standard adaptive hashing (Argon2id or bcrypt).
4. Unauthenticated guest rate limits must apply until authentication is verified per [[req-202609121912]].

---

## Edge cases and errors

- **Email Already Registered with Another Provider:** If an email registered via Google tries to log in with password, return clear message: "Este e-mail está associado ao login com Google. Faça login pelo botão Google."
- **Social OAuth Cancellation:** If seeker cancels the Google or Facebook dialog, close the popup and return to modal without error crash.
