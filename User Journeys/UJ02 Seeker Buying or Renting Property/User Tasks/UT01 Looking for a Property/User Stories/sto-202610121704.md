# User Story: Multi-Criteria Structured and Semantic Vector Property Search

---

## Summary

- **As a** property seeker looking to buy or rent real estate,
- **I want to** filter properties by City, neighborhood, cardinal regions (North, South, East, West, Center), price minimum and maximum, number of rooms, suites, architectural kind (House, two-story house, apartment, gated community), or submit natural language lifestyle queries via Semantic Vector Search,
- **So that** I receive an accurate list of candidate properties matching my spatial, financial, and lifestyle preferences.

---

## Scope in/out

- **In Scope:** Search query input supporting structured filtering (City, neighborhood, cardinal regions, price min/max, bedroom count min, suite count min, property typology: `house`, `two-story house` / `sobrado`, `apartment`, `gated community`), transaction intent toggle (Buy / Rent), natural language semantic query processing via dense vector embeddings per [[con-202609121901]], dynamic irrelevance floor pruning, hybrid SQL metadata and vector scoring, result sorting (relevance, price ascending/descending), and pagination.
- **Out of Scope:** Rendering interactive map pins and boundaries (handled in [[sto-202610121705]]), toggling amenity layers (handled in [[sto-202610121706]]), and managing saved preference lists.

---

## Preconditions

1. Tenant database and vector collections provisioned and isolated per [[run-202609121908]] and [[req-202609121910]].
2. Semantic vector search engine operational per [[con-202609121901]].
3. Web portal search API endpoints deployed and reachable.

---

## Expected behavior

When a seeker inputs filter criteria or types a natural language query in the search bar, the platform executes a hybrid query combining structured SQL metadata filtering with vector similarity retrieval within the tenant's isolated data collection, applies the dynamic irrelevance floor algorithm, and renders matching property summary cards.

---

## Acceptance criteria

### Criterion 1: Transaction Intent and Geographic Boundary Filtering
- **Given** a property seeker navigating the search interface,
- **When** the seeker selects transaction type ("Comprar" / Buy or "Alugar" / Rent), City (e.g., "São Paulo"), Neighborhood (e.g., "Pinheiros"), or Cardinal Region ("Zona Norte", "Zona Sul", "Zona Leste", "Zona Oeste", "Centro"),
- **Then** the search engine must restrict results strictly to listings matching the selected transaction mode and geographic boundaries.

### Criterion 2: Price and Room Configuration Filtering
- **Given** a seeker specifying financial and layout limits,
- **When** the seeker inputs minimum price, maximum price, minimum bedroom count (e.g., >= 2), and minimum suite count (e.g., >= 1),
- **Then** only properties meeting all numerical criteria must be included in the results list.

### Criterion 3: Architectural Typology Selection
- **Given** a seeker filtering by property category,
- **When** the seeker selects one or more typologies from:
  - House (`casa`)
  - Two-story house / Townhouse (`sobrado`)
  - Apartment (`apartamento`)
  - Gated community house (`casa em condomínio`)
- **Then** the platform must filter listings to display only items tagged with the selected architectural types.

### Criterion 4: Natural Language Semantic Vector Search
- **Given** a seeker entering a descriptive lifestyle query (e.g., "apartamento bem iluminado com sol da manhã e varanda para home office"),
- **When** the query is submitted,
- **Then** the search engine must generate dense vector embeddings, compute cosine similarity against tenant listing embeddings, and apply the dynamic irrelevance floor (`cutoff = max(0.40, top_score - 0.25)`) per [[con-202609121901]] to prune low-relevance results.

### Criterion 5: Zero-Match Fallback and Graceful Feedback
- **Given** search criteria that yield no database matches or where all candidate scores fall below 0.40,
- **When** the search executes,
- **Then** the interface must display a polite zero-results message with clear suggestions to broaden filters or adjust price limits without UI freeze.

## Contracts and data

- **Endpoint:** `POST /api/v1/properties/search`
- **Request Format:** `application/json`
- **Example Request Payload:**
```json
{
  "transaction_type": "buy",
  "city": "Sao Paulo",
  "neighborhood": "Pinheiros",
  "cardinal_region": "west",
  "price_min": 500000.00,
  "price_max": 1200000.00,
  "bedrooms_min": 2,
  "suites_min": 1,
  "typology": ["apartment", "sobrado"],
  "query": "apartamento ensolarado com varanda e suite",
  "page": 1,
  "page_size": 20
}
```
- **Example Response Payload:**
```json
{
  "total": 14,
  "page": 1,

      "title": "Apartamento Iluminado em Pinheiros",
      "transaction_type": "buy",
      "typology": "apartment",

    }

```

## Business rules

1. All searches must execute strictly within the isolated tenant database and vector collection per [[req-202609121910]] (No Shared Pools).
2. The dynamic irrelevance floor must execute autonomously (`cutoff = max(0.40, top_score - 0.25)`). If the top score falls below 0.40, the system returns zero items (`total: 0, items: []`).
3. Requests must respect public rate limiting quotas defined in [[req-202609121912]].
4. Prices must be represented in Brazilian Reais (BRL).

---

## Edge cases and errors

- **Negative or Inverted Price Range:** If `price_min > price_max`, the system automatically swaps values or displays a client validation warning.
- **Vector Search Latency:** If the embedding service latency exceeds 1200 ms, the query gracefully degrades to lexical full-text SQL matching.
